# PRD：游戏 H5 网页版发布

| 项 | 内容 |
|---|---|
| 文档版本 | v1.0 |
| 日期 | 2026-11-24 |
| 项目 | MY GAME（Godot 4.7.2 / 纯 GDScript） |
| 交付形态 | 浏览器可打开的静态站点（`index.html` + WebAssembly） |
| 关联决策 | 方案 A：保留 Godot 工程，导出 Web，不重写逻辑 |

---

## 1. 背景与问题

游戏目前只能在装了 Godot 引擎的机器上通过命令行运行，别人拿到 GitHub 仓库后无法直接玩，也没法在手机上打开。需要一个"点开链接就能玩"的版本。

选择 Godot 官方 Web 导出的理由：项目 100% 由代码构建场景，所有图形都是 `_draw()` 画的圆与多边形，**没有任何外部美术素材**。因此导出包只包含引擎本体，不携带图片资源，是 Godot 工程里最轻的一种情况。

### 当前阻碍导出的硬条件（已实测确认）

| # | 问题 | 现状 | 结论 |
|---|---|---|---|
| A | 渲染后端 | `config/features` 写死 `Forward Plus` | Web 不支持 Vulkan/Forward+，必须先切 GL Compatibility |
| B | 字体 | `UiKit.font()` 用 `SystemFont` + `["Microsoft YaHei", "SimHei", "Segoe UI"]` | **Web 平台无系统字体访问能力**，SystemFont 会退化到引擎内置 OpenSans，中文字全部变方块 |
| C | 视口尺寸 | 未显式设置 | 需固定基准分辨率 + 自适应策略，否则手机上会被裁切 |
| D | 输入 | 仅键盘（WASD + 空格） | 桌面浏览器可用；手机端已由虚拟摇杆补齐（§9） |
| E | 导出模板 | 未安装 | 必须下载 Web 导出模板，否则导出按钮不可用 |
| F | 物理引擎声明 | `3d/physics_engine="Jolt Physics"` | Web 模板不含 Jolt，2D 游戏用不到，应移除以避免启动告警 |
| G | 存档持久化 | `user://records.json` | Web 下映射到浏览器 IndexedDB，需确认刷新后不丢档 |

## 2. 目标与非目标

### 目标

1. 在桌面浏览器（Chrome / Edge，支持 WebGL2）打开链接即可游玩，操作与桌面版一致。
2. 手机横屏打开时用虚拟摇杆 + 技能键即可完整游玩（不依赖任何键盘）。
2. 中文菜单、HUD、昵称输入全部正常显示，无方块字。
3. 历史最高分在关闭标签页、重开浏览器后仍然保留。
4. 首屏从打开到可操作 ≤ 10 秒（本地 / 常规宽带）。
5. 产物为纯静态文件，可部署到任意静态托管（GitHub Pages、Vercel、对象存储）。

### 非目标（本期不做）

- 微信小游戏（Godot 无该导出目标，且主包 4MB 限制无法满足）
- 多人联机、账号系统、排行榜服务器
- 音效 / 音乐（项目当前无音频系统）
- 替换 `_draw()` 占位图形为真实美术
- 重写玩法逻辑

## 4. 需求明细

### R1 · 渲染后端切换（P0）

- `project.godot` 中 `config/features` 由 `("4.7", "Forward Plus")` 改为 `("4.7", "GL Compatibility")`。
- 显式声明 `rendering/renderer/rendering_method="gl_compatibility"` 与 `rendering_method.mobile="gl_compatibility"`。
- **回归风险**：`damage_vignette.gdshader`（低血红边）需在 GL Compatibility 下重新验证；`_draw()` 全部为 2D 图元，不受影响。
- 桌面端本地运行效果不得改变（`--headless` 与开窗各跑一遍零报错）。

### R2 · 中文字体内嵌（P0，核心）

- **放弃 `SystemFont`**，改为内嵌字体文件 + `FontFile`。
- 字体选型：Noto Sans SC（OFL 协议，可商用可分发）。
- **必须做子集化**，否则完整字库约 10MB，会明显拖慢加载：
  - 覆盖范围 = GB2312 一级+二级汉字（6763 字）+ ASCII + 全角标点 + 游戏内固定文案全部字符。
  - 目标体积 ≤ 3MB（gzip 后 ≤ 1.5MB）。
- 昵称由玩家输入，**生僻字可能显示为方块**——这是子集化的已知取舍，在 PRD 中记录为可接受。若后续需要全覆盖，改用完整字库并接受体积代价。
- 实现方式：`UiKit.font()` 返回 `FontFile`（`load("res://assets/fonts/NotoSansSC-subset.otf")`），调用方签名不变（`Label` / `draw_string` 都接受 `Font`）。
- 兜底：字体加载失败时退回 `ThemeDB.fallback_font`，不得因字体缺失导致脚本报错。

### R3 · 视口与响应式（P0）

- 基准分辨率：`1280 × 720`（16:9），写入 `display/window/size/viewport_width/height`。
- `window/stretch/mode="canvas_items"`、`aspect="expand"`（已具备，保留）。
- 浏览器窗口任意比例下：HUD 不裁切、不重叠；超宽屏时以 16:9 为安全区，边缘留空。
- 竖屏（手机）显示"请横屏游玩"提示层，横屏后自动消失（P1 一并做）。

### R4 · 移动端触屏输入（P1 → 已完成，实现见 §9）

- 左下角虚拟摇杆：触摸拖动 → 映射到 `move_left/right/up/down` 四个动作（复用现有 InputMap，不改玩家移动代码）。
- 右下角技能按钮：满蓝时高亮，触摸触发 `cast_skill`。
- 摇杆用 `Control` + `_gui_input` 实现，仅 `OS.has_feature("web")` 且检测到触摸设备时显示；桌面浏览器不出现。
- 触摸区不得遮挡 HUD 与升级三选一卡片。

### R5 · 加载体验（P0）

- 自定义 HTML 加载页：游戏标题 + 进度条 + "首次加载约需 X 秒"提示，替换 Godot 默认黑屏。
- 引擎启动后隐藏加载页，禁止出现白屏闪烁。
- 加载失败（WebGL2 不可用）时给出明确中文提示，而不是静默黑屏。

### R6 · 存档持久化（P0）

- Web 下 `user://` 落在 IndexedDB。需实测：写入最高分 → 刷新页面 → 记录仍在。
- 若发现丢失，在 `ScoreBoard.save()` 后显式调用同步点（Godot 4 Web 的 `OS` 无直接 flush API，需靠引擎周期性同步；必要时改为写完后 `await` 一帧再提示）。
- 不做跨设备同步。

### R7 · 导出与部署（P0 → 已完成，公网部署见 §10）

- 安装 Web 导出模板（约 1GB，含各平台；仅用 Web 部分）。
- 新增 `export_presets.cfg`，预设名 `Web`，包含：
  - 导出路径 `build/web/index.html`
  - `variant/extensions_support=false`（不需要扩展）
  - `vram_texture_compression/for_desktop=false`
  - 线程支持关闭（单线程，避免 COOP/COEP 跨源隔离要求，方便任意静态托管）
- 产物目录 `build/` 加入 `.gitignore`（构建物不入库）。
- 提供 `serve.py` 或一行命令启动本地服务器（**不能直接双击 index.html**，浏览器禁止 `file://` 下加载 wasm）。

### R8 · 工程清理（P2）

- 移除 `3d/physics_engine="Jolt Physics"`。
- `rendering_device/driver.windows="d3d12"` 仅影响 Windows 本地，Web 忽略，可保留。
- 中文文件名（`MY主场景.tscn`）在 pck 内为 UTF-8，Web 导出无影响，暂不改名。

## 6. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 字体压缩后仍偏大 | 首屏慢 | 严格子集化；字体单独走 CDN 缓存头 |

### 已知限制

1. **打字仍需系统输入法**：昵称输入框是原生 `LineEdit`，手机浏览器下不一定弹出软键盘（Godot Web 的可选框内键盘还是实验特性，开启后会抢键盘事件，影响 WASD，故未启用）。规避方式：默认昵称「玩家」直接可开局，或点战绩榜里的历史记录开局。
2. **昵称生僻字可能显示方块**：字体做了子集化，只覆盖 GB2312 常用字。
3. **首屏受网速影响**：10MB 传输在 4G 下约 5~15 秒。
4. **不支持 `file://` 直接打开**：必须经 HTTP（`python serve.py`）。
5. **低端机可能掉帧**：手机端可见世界范围比桌面小（960 基准反而放大了物体），同屏敌人数量由存活时间决定，未针对移动 GPU 单独限流。

### 复现命令

```bash
# 导出（先建目录，Godot 不会自动创建）
mkdir -p build/web
godot --headless --path . --export-release "Web" build/web/index.html
# 预览
python serve.py 8080     # 打开 http://127.0.0.1:8080/
```

导出前必须先建好 `build/web` 目录，Godot 不会自动创建，否则报"目标文件夹不存在"。

## 9. R4 触屏操作（2026-11-24 完成）

### 设计取舍

| 决策 | 做法 | 为什么不那么做 |
|---|---|---|
| 摇杆怎么驱动移动 | `Input.action_press()` 写进 `move_left/right/up/down`，带 0~1 强度 | 直接改 `Player.global_position` 会和键盘抢状态，还要在 Player 里加"触屏模式"分支；走 InputMap 后玩家代码一行未动，模拟量天生支持（推一半走半速） |
| 摇杆位置 | **浮动**：按在圈里用画的底盘，按在别处则底盘挪到指尖下 | 固定底盘在 5 寸屏上要"先找再按"，横屏时拇指落点每次都不一样 |
| 触摸事件走哪 | `_input` 手动做区域命中，不用 `_gui_input` | 摇杆感应区覆盖左半屏，做成 Control 会把这块区域变成"吃掉点击"的控件，还得在暂停时收拾 |
| 桌面怎么调试 | `godot --path . -- --touch`：强制开触屏 + 鼠标当单指 | 不开真机也能拖摇杆验收 |
| 手机分辨率 | 触屏设备把逻辑分辨率从 1280×720 降到 960×540 | 844×390 的机器上 16px 字号只剩 8 个 CSS 像素，血条数字看不清 |
| 结算页操作 | 触屏模式把「R 再来一局 / P 换人」换成两个大按钮 | 手机上既没有 R 也没有 P，不改就是死路 |
| 技能键 | 右下角圆形按钮，蓝量画成圆环，满蓝变金 + 呼吸光环 | 手机上没有空格键，HUD 的"空格 · 技能名"在触屏下改成"点按 · 技能名" |

### 关键实现细节

- **多指**：摇杆与技能键各记一个手指 id，左手推着走、右手点技能互不打断（实测验证）。
- **暂停收起**：升级选卡 / 结算 / 菜单时整层隐藏并强制松开所有移动动作，否则暂停时角色会带着残留输入继续滑。
- **坐标系**：尺寸全部按"视口高度 / 540"缩放，画布坐标由引擎的 stretch 变换统一处理，桌面 720 与手机 540 两套基准都不用改常量。
- **顺手修的旧 bug**：升级卡的图标底板是 `PanelContainer`（默认 `MOUSE_FILTER_STOP`），点卡片图标那一块原来什么都不发生——桌面端也一样。已改为 `IGNORE`，整张卡都能点。

## 10. 公网部署到 GitHub Pages（2026-11-24 完成）

**在线地址：<https://xumingxian29.github.io/MYGAME/>**

### 10.1 这条路为什么能走通

三件事凑齐才成立，少一件都要换方案：

| 前提 | 本项目的情况 |
|---|---|
| 不需要 COOP/COEP 响应头 | 用 **nothreads** 模板导出，不依赖 `SharedArrayBuffer`。GitHub Pages 无法自定义响应头，这一条是决定性的 |
| 资源路径必须是相对的 | 加载页里只有 `index.js` / `index.wasm` / `index.pck` 三个相对引用，没有以 `/` 开头的绝对路径，所以放在 `/MYGAME/` 子目录下能正确解析 |
| wasm 要能被流式编译 | GitHub Pages 对 `.wasm` 返回 `application/wasm`（实测确认），`WebAssembly.instantiateStreaming` 直接可用 |

### 10.2 发布方式：`deploy_pages.sh`

```bash
./deploy_pages.sh              # 导出 + 推送
./deploy_pages.sh --no-export  # 只重推现有 build/web
```

脚本做四件事，每一步都有个明确的"为什么"：

1. **白名单挑文件**，不用 `cp build/web/*`。产物目录里还有 `.import`（编辑器生成的资源元数据）和 `.gzcache`（`serve.py` 的 gzip 缓存），传上去纯属噪音。
2. **写一个空 `.nojekyll`**。否则 GitHub 会先拿 Jekyll 处理一遍静态站点，纯属浪费，还可能吞掉下划线开头的文件。
3. **在 `build/pages` 里新建一个临时仓库**，只提交这一次的内容。
4. **`--force` 推送到 `gh-pages`**。

第 3、4 步是刻意的：wasm 单文件 39.5MB，如果每次发布都往同一分支追加提交，十几次之后仓库就是几百 MB，克隆会变得很慢。强推单提交后，`gh-pages` 分支永远只有一个 commit，仓库体积只跟当前构建有关。

仓库 **Settings → Pages** 的 Source 已经是 `gh-pages / (root)`（通过 API 读到 `source.branch = gh-pages`, `build_type = legacy`），所以每次推送后 GitHub 会自动重新构建，不需要再点任何东西。

## 11. 毒圈（BR 缩圈）与时长收敛（2026-11-24 夜，P1）

### 11.1 为什么要做：时长不是"随机"，是三个结构性漏洞

加圈之前先量了基线（`dev/bot.gd`，4 策略 × 3 种子，上限从 420 抬到 780 秒）：

| 策略 | 中位存活 | 最短 | 最长 | 说明 |
|---|---|---|---|---|
| idle（不操作） | 75.4s | 74.1 | 80.8 | 下限参照 |
| idle_skill（不操作但放技能） | 146.8s | 136.2 | 152.5 | "轮椅"假设的最坏情况 |
| kite_skill（战士，正常玩法） | 549.6s | 157.9 | 683.0 | 会玩的人能拖到 9~11 分钟 |
| kite_ranged（射手，正常玩法） | **780.0s（撞上限）** | 196.1 | 780.0 | 3 局里 2 局打到 13 分钟仍未死，终血 110/110 |

射手那两局是决定性的证据：**满血、3 万杀、平均敌人存活 1.4~2.2 秒**——它把怪清在屏幕外，
根本没被碰到。对应三条根因：

1. **章节时钟在 Boss 战期间暂停**：`_stage_time` 只在 `_boss == null` 时才走。打不动 Boss 就永远不换章，也永远死不了。
2. **敌人有数量上限，且分离逻辑把人墙推开**：`_enemy_budget()` 封顶 420（手机 210），成型 build 能无限绕圈。
3. **世界无限大**：`_spawn_offset()` 永远在视野外接椭圆上刷怪，直线跑就只会遇到同速或更慢的敌人。

毒圈同时封住这三条：空间有限→绕不了整场；圈缩进视野→四面同时逼近；圈缩到 0→必死。

### 11.2 缩圈表

半径以**视野半径 V** 为单位（桌面 1280×720/zoom 1.35 → V≈545；手机 960×540 → V≈408）。
写死像素的话，手机会看到比桌面大 33% 的圈，同一套时间轴手感完全不同。

| 时间 | 半径 | 圈外毒伤 | 阶段 |
|---|---|---|---|
| 0:00–1:50 | 2.20V | 0 | 安全区稳定（圈在屏幕外，纯送分） |
| 1:50–2:20 | →1.50V | 1.0%/s | 第一次收缩 |
| 2:20–3:05 | 1.50V | 1.0%/s | 稳定（给足第一章时间） |
| 3:05–3:35 | →1.10V | 1.6%/s | 紫墙第一次贴到屏幕边缘 |
| 3:35–4:15 | 1.10V | 1.6%/s | 稳定（与第二只 Boss 重叠） |
| 4:15–4:45 | →0.85V | 2.5%/s | 边界进屏幕，"跑出去"真的掉血 |
| 4:45–5:25 | 0.85V | 2.5%/s | 稳定 |
| 5:25–5:55 | →0.62V | 4.0%/s | 必须挪位 |
| 5:55–6:30 | →0.45V | 6.0%/s | 决战 |
| 6:30–8:00 | →0 | 10%→18%/s | 终局，8:00 前必然结算 |

两条不变量：

- **新圈必须完整落在旧圈内**：`圈心 += 随机方向 × (R旧−R新) × 0.55`。系数取 0.55 而不是 1.0，
  是为了"明显要挪位"但不"横穿整张地图"；≥1.0 会出现新圈在旧圈外的无解局面。
- **毒伤按最大生命的百分比**：三职业血量 180/100/110，固定扣血会让法师被圈秒、战士无感。

### 11.3 实现要点（都是"不这样就会坏"的地方）

| 决策 | 原因 |
|---|---|
| 毒伤走独立的 `Player.take_zone_damage()` | `take_damage()` 开头就是无敌帧返回，而受击无敌 0.45s 比毒伤 0.5s 一跳还长——走老入口会让"被贴身打的时候反而不掉毒血" |
| 毒伤不闪白、不抖屏、不给无敌 | 玩家要从血条和红边读出"我在掉血"，闪光只会干扰判断 |
| 敌人不吃毒 | 否则圈替玩家清场，白送击杀与经验，Boss 战变成"等圈杀 Boss" |
| 刷怪点夹进 1.03R | 半径小于视野时，"视野外"的点会落在毒里，怪永远走不到玩家面前；夹在壁外一点，视觉上是"从紫幕里钻出来" |
| Boss 生成也夹 | 同上，且 Boss 从紫幕外走进来像逃课 |
| 圈心与半径一起插值 | 只在段首跳变的话，安全区会瞬移，玩家没法跟 |
| HUD 报时间不报半径 | 玩家真正需要的是"还有几秒"，半径用眼睛看那条紫线 |
| 屏外方向箭头 | 圈心每轮挪位，缩到 0.85V 后边界可能整块滑出屏幕；这时只有"圈外 -11%/s"的红字，玩家不知道往哪跑 |

### 11.4 自检（`dev/zone_probe.gd`，67/67 通过）

### 11.5 两版实测对照（`dev/bot.gd`，12 局 = 2 策略 × 5 种子 + 2 个下限参照）

kite 只看 10 局（战士 5 + 射手 5），idle 两局是下限参照、不参与中位数：

| 版本 | 中位存活 | 最长 | 越过圈归零时刻 | 圈外致死 |
|---|---|---|---|---|
| 无圈基线（上限 13:00） | 549.6s（战士）/ 780s 撞顶（射手） | 780.0s | — | — |
| 第一版 11:30 | **691.0s** | 693.9s | 0 局 | 42%（12 局口径） |
| **第二版 8:00** | **483.1s** | **484.1s** | **0 局** | 58%（12 局口径），kite 内 7/10 = 70% |

第二版细节：kite 10 局里 8 局在 482~484s 结算（圈归零），另 2 局是战士 200.1s / 206.3s 被怪围死、
射手 112.8s 被抓；idle 78.3s、idle_skill 166.5s 与第一版基本一致（那时圈还没缩，说明早期节奏没被动过）。

**结论：时长达标，难度没达标。**

- 时长：482s = 8:02，落在"5~10 分钟"窗口内，最长 484.1s，没有任何一局越过 8:04。
- 难度：58% 死于圈外，而且那 8 局在 482s 时**血量是满的**（战士 180/180、射手 110/110、杀敌上万）。
  也就是说后期没有威胁，**圈只是计时器**，不是战斗。

根因是速度：敌人速度上限 `94 + 46 = 140`，玩家 240。会走位的人在开放场地上永远不被追上，
后期唯一的死法就是圈缩没。修这个要动难度曲线，而不是继续缩圈（继续缩只是让计时器更早响）：

1. 后期加"追得上"的单位（冲刺型精英 / 短时加速追猎），逼玩家换位而不是无限绕圈；
2. 章节倍率之外再加一条时间威胁曲线：吐酸者比例、弹幕密度随 elapsed 上升；
3. `ENEMY_SPEED_CAP` 抬到 170~190——仍低于玩家，但紧到"绕圈必须贴边"。

这三条都会改动全局手感，属于 P2，等确认后再做。

### 11.6 后期难度曲线（2026-11-25，P2 第一版）

#### 第一次尝试：错在"全程"而不是"后期"

`ENEMY_SPEED_CAP` 46→81（总速 140→175）+ 吐息者占比按 elapsed 全程线性 +0.20。结果：

| 策略 | 改动前中位 | 改动后中位 | 说明 |
|---|---|---|---|
| kite_skill 战士 | 483.1s | **184.6s** | 157.8 / 165.7 / 184.6 / 192.3 / 255.6，全线崩 |
| kite_ranged 射手 | 483.1s | 483.1s | 一点没变 |
| idle_skill | 166.5s | 114.0s | 连"轮椅"都被压 |

结论：速度上限这条线管的是**中期会不会被围住**，不是后期。把它抬高，等于把开局到中期的
所有死亡时间一起前移——这已经不是"后期更难"，是"全程更难"。而射手 252 的移速下，
任何 175 的敌人都追不上，改速度对它完全无效。

#### 采用的做法：时间门控，0~240 秒一个字节都不许变

```
_threat() = clamp((elapsed - 240) / 150, 0, 1)   # 240 秒起爬，390 秒爬满
速度        += 28 * _threat()      # 总速 140 → 168（仍低于任何职业）
吐息者占比  += 0.20 * _threat()    # 唯一不贴身就能造成伤害的敌人
特殊怪总占比封在 0.70               # 留三成普通小兵，不然人墙没了反而更好清
```

`ENEMY_SPEED_CAP` 回调 46。**验收标准是"早中期数据与上一版完全一致"**——
这不是手感问题，而是可测的：任何一点偏移都说明曲线起点错了。

#### 13 局实测（8:00 时间轴 + 难度曲线）

| 版本 | kite 中位 | 最长 | 圈外致死 | 圈归零前死于敌人 |
|---|---|---|---|---|
| 8:00，无难度曲线（§11.5） | 483.1s | 484.1s | 58% | 0 局 |
| 8:00 + 全局加速（已废弃） | 184.6s | 255.6s | 33% | 5 局（都在 3 分钟内） |
| **8:00 + 时间门控曲线** | **460.3s** | **483.6s** | **42%** | **2 局（460.0 / 460.6）** |

时间门控的证据很硬：0~240 秒内的死亡时间与上一版**逐秒相同**——战士 200.1 / 206.3、
idle 78.3、idle_skill 166.5；而三局原本"满血拖到圈缩没"的战士，现在 477.9（圈）、
460.0（敌人）、483.6（圈）；射手第一次在 460.6 死在敌人手里而不是圈里。

#### 还剩什么

42% 仍高于 15~35% 的目标，但性质变了：从"计时器"变成"压力"（有两局在圈归零前 20 秒被围死）。
继续加大这条曲线只会重演第一次的失败。真正的瓶颈在职业平衡——射手在 460 秒仍有
23 杀/秒、平均敌人存活 0.2 秒，任何靠"追上来"的威胁对 252 移速的远程都无效，
要动它必须改武器或改远程的输出曲线，那是另一个话题。

自检：`stage_check` 全部通过、`boss_check` 58 项全部通过（Boss 也吃这条曲线）、
`zone_probe` 67/67。

## 12. 关底 Boss 的攻防循环（2026-11-25 夜，P3）

### 12.1 问题：壳把 Boss 变成了"弹药检查"

破甲弹上线后，实测 4 局（seed=11）暴露了两个反直觉的数：

| 角色 | 第 1 只 Boss | 第 2 只 | 第 3 只 |
|---|---|---|---|
| 战士 | 39s | 35s | — |
| 射手 | **9s** | **8s** | **9s** |

射手和战士的武器、血量、移速都不一样，唯一说得通的解释是"手上攒了几发弹"：
破甲弹伤害固定 40、锁 0.25 秒，12 发弹打 480 血只需要 3 秒倾泻。
也就是说**Boss 的存活时间由弹药库存决定，玩家的操作不影响**——
那不是难度，是一次资源清算。

### 12.2 做法：把"能不能打"变成一个时间窗口

Boss 进入三态循环，玩家能做和不能做被写死：

| 状态 | 时长 | Boss | 玩家 |
|---|---|---|---|
| 追击 | ≤2.4s，进 200 就提前结束 | 可移动 · 无敌 | 拉开距离、捡弹 |
| 连招 | 3~6s（一阶段 3 招 / 二阶段 4 招） | **定身 · 无敌** | 读前摇、躲 |
| **破甲** | **3.0s** | 定身 · **可被破甲弹伤害** · 半速向玩家蹭 | 贴上去把弹打空 |

三条约束是有互相依赖的，改一条必须回头看另外两条：

1. **窗口必须短于连招段**（3.0 < 4.1）。反过来的话节奏变成"打多躲少"，
   读招就没有价值了，Boss 战会退化成轮流互殴。
2. **窗口里 Boss 必须能挪**（半速）。定身的话会出现死局：玩家为了躲招退到 400 外，
   窗口开了它原地不动，3 秒跑不回来——整场变成"谁离得近谁赢"。半速是"它会靠近，但绝不如你快"。
3. **不能在出招阶段扣弹**。打早了只闪冷色火花、不消耗资源；
   扣弹会让玩家学会"不敢开枪"，而这条机制的全部乐趣来自"敢在窗口里把弹打空"。

### 12.3 新招式：裂地（`MOVE_STRIKE`）

旧招式全是"一发，躲完就结束"，玩家的最优解永远是站着输出、看到前摇再侧移一步。
裂地是唯一一招**持续 2.4 秒、连续五处落点**的招式：

- 抬手 0.7s → 之后每 0.42s 在玩家脚下开一处，半径 76；
- 落点 = 玩家位置 + `velocity × 0.55s`。站桩必中，直线跑会被算中，**只有变向能躲**；
- 由 `scripts/boss_strike.gd` 独立结算（世界坐标的预警圈），Boss 只负责"落在哪"。

三套 kit 表都排进了这一招——它是"出招三秒、全程无敌"这个节奏的载体，
只有一只 Boss 会的话，另外两场的 Boss 战还是旧手感。

### 12.4 配平：血量和掉率必须一起动

| 章 | 发数（原→现） | 掉率（原→现） | 单场估算 |
|---|---|---|---|
| 一 | 12 → **18** | 4.0 → **2.4s** | 26s |
| 二 | 16 → **23** | 4.5 → **2.5s** | 35s |
| 三 | 20 → **28** | 5.0 → **2.6s** | 44s |

只抬血量不抬掉率，Boss 会拉成 60 秒的拉锯；只抬掉率不抬血量，两个窗口就打完。
`dev/breach_check.gd` 把"发数 × 掉率 × Game 的 0.6 倍"当成断言（25~45 秒），
0.6 从 Game 读而不是写死——写死的那个数（`bot.gd` 曾经的 690）改表就失效。

### 12.5 时间预算冲突 → 圈放宽到 6:30（已解决）

Boss 攻防循环把每场从 9~12 秒拉到 26/35/44 秒（合计 **105 秒**），而章节本身要
70+80+90 = **240 秒**，加起来 345 秒。第三版毒圈只有 304 秒，少了 41 秒——
**这个版本打不完第三章**，第三只 Boss 在圈归零前不会出现。

两个解法，选了第 2 个：

| 解法 | 账 | 不选的理由 |
|---|---|---|
| 1. 章节压到 50/55/60（165s） | 165 + 105 = 270s，塞得进 5:04 | 压章节会同时压掉经验与卡片成长，动的是全局手感 |
| **2. 圈放宽到 6:30（390s）** | **240 + 105 = 345s，余 45s** | 采用 |

第四版时间轴（`zone.gd`）：**半径序列一格不动，六段收缩速度也一格不动，只把三个稳定段
从 22/18/16 拉成 56/48/38**（+86 秒）。加的全是"等"的时间，不改"圈收得多快"——
后者是难度，前者只是时长。三个稳定段仍然递减，保留"越到后期喘气越少"这条性质。

| 段 | 第三版 5:04 | 第四版 6:30 |
|---|---|---|
| 开局不缩 | 0–110 | 0–110 |
| 第 1 次收缩 | 110–140 | 110–140 |
| 稳定 | 140–162（22s） | 140–196（**56s**） |
| 第 2 次收缩 | 162–186 | 196–220 |
| 稳定 | 186–204（18s） | 220–268（**48s**） |
| 第 3 次收缩 | 204–226 | 268–290 |
| 稳定 | 226–242（16s） | 290–328（**38s**） |
| 第 4 次收缩 | 242–262 | 328–348 |
| 决战 | 262–280 | 348–366 |
| 终局 →0 | 280–304（24s） | 366–390（24s） |

`dev/breach_check.gd` 里那条预算断言也一起改成**从两张表读**（Stage 的 `length`、
Zone 末段的 `to`），原来写死成 `fight_total <= 130`——圈从 480 压到 304 时它照样报 ok，
正是"改表即失效"的同一类错误。

> 毒圈不再挂进 world，一局没有时间上限。保留原文是为了留下"为什么当时这么调"的记录。

## 13. 地图循环：迷宫、传送门与楼层难度（2026-11-28）

### 13.1 去掉毒圈，边界改由迷宫承担

玩家和敌人都是直接改 `global_position`，没有物理体，所以墙**不能靠碰撞体**实现。
`MazeMap` 只提供查询，不反向持有玩家：

| API | 用途 |
|---|---|
| `is_walkable_cell` / `has_floor_at` | 判定 |
| `constrain(from, to, radius)` | 位移后夹紧，贴墙滑动 |
| `rebuild_flow(player_pos)` | 从玩家所在格做一次 BFS，换格才重算（432 格） |
| `flow_dir(pos)` | 敌人绕墙的方向场（不给每只怪跑 A*） |
| `nearest_floor_point` / `random_spawn_point` | 掉落与刷怪落点 |

9 个房间 + L 形走廊，`CELL = 96`，网格 24×18。同一 seed 逐格可复现（台架做 A/B 的前提）。

### 13.2 传送门：Boss 死后开三扇

| 项 | 值 | 理由 |
|---|---|---|
| 数量 | 3 | 三种奖励各一扇 |
| 位置 | Boss 尸体周围 130~400，8 方向试探 | 走廊里固定角度会三扇叠成一扇 |
| 保护期 | 1.6 秒 | Boss 死时玩家正站在尸体上捡宝石 |
| 触发半径 | 30（外环 46） | 擦边不算进，要真的走进去 |
| 阶段 | `CARD` / `BREACH +3` / `HEAL 35%` | 选"带什么进去"，不是选难度 |

挑门期间**停刷、停 Boss 检查、章节时钟不再推进**（`_awaiting_portal`）。
不挡的话玩家在门口挑十秒，会凭空多出一只 Boss、或者进门第一帧就是满编一波。

### 13.3 楼层难度：每道门 ×1.10

`_floor` 记录穿过的门数，`_power_scale() = 1.10 ^ _floor`，乘在**最终数值**上：

| 属性 | 是否吃倍率 | 说明 |
|---|---|---|
| 血量 | 是（累乘） | 放在精英/自爆等身份修正之后，相对关系不漂 |
| 速度 | 是，但封顶 1.5× | 1.10^6 就超过玩家移速，那不是难度是判死刑 |
| 接触 / 冲刺 / 自爆 / 吐息伤害 | 是 | 走 `Enemy.power_scale`，一条全出口规则 |
| Boss 血量 | **否** | Boss 血 = 破甲弹发数 × 40，随难度乘会破坏配平 |

同时把 `Stage._endless` 的 `ENDLESS_HP_STEP` 从 1.3 降到 **1.0**：
两项叠起来每关 1.43 倍，第五张图的怪会是第一张的 3 倍。一个乘数只能有一个来源。

### 13.4 敌人配比：少而硬

| 项 | 旧 | 新 | 备注 |
|---|---|---|---|
| `BUDGET_BASE` / `BUDGET_STEP` | 12 / 4.0 | **9 / 5.5** | 390s 上限 109 → 79 |
| `SPAWN_INTERVAL_EASY/HARD` | 0.7 / 0.28 | **0.95 / 0.46** | 单波产出减半 |

| `xp_value` 普通/精英/特殊 | 2 / 6 / 3 | **4 / 12 / 6** | 数量减了，经验必须补，否则负循环 |

## 14. 暂停键与返回键（2026-11-28）

### 14.1 为什么不能只加一颗暂停键

项目原来只有两种暂停来源：`State.LEVEL_UP`（选卡）和 `State.GAME_OVER`（结算），
两者都是"游戏已经替我停了"。玩家主动暂停是第三种，而且它是**可进出**的：
其余两种状态只能由游戏单向推进，不允许玩家按回去。

所以新增的是第五个状态 `PAUSED`，而不是给 `paused` 打补丁：

- 冻结仍由 `_sync_pause()` 统一裁决（`paused = 外部打断 或 _state != PLAYING`），
  暂停面板不直接写 `get_tree().paused`；
- `_physics_process` 开头那句 `if _state != PLAYING: return` 原样生效，
  `_elapsed`、刷怪、Boss 计时全部停住（Game 是 `PROCESS_MODE_ALWAYS`，
  它自己的 `_physics_process` 照常被调用，靠的就是这句提前返回）；
- `_on_pause_toggled()` 只允许 `PLAYING ↔ PAUSED` 这一条边。选卡与结算时按暂停键无效，
  否则会出现"暂停面板盖在选卡卡片上"这种谁也没法关的双层弹窗。

### 14.2 两颗按钮的分工

| | 位置 | 行为 | 原因 |
|---|---|---|---|
| 暂停 | 右上，分数下方，72×38 | 切换暂停，文字变「继续」 | 复用同一颗按钮，手机上多一颗就多一片误触区 |
| 返回 | 紧挨暂停右侧，灰蓝色 | 直接回主菜单 | 主目标是手机；主菜单保留昵称与最高分，重开成本低。灰蓝色是刻意的：误触代价是一整局，视觉上要先让人犹豫 |

暂停面板（居中）给三个入口：继续 / 重新开始 / 返回主菜单。
只做"继续"的话，玩家想换一局还是得先死一次——而暂停恰恰是他最想退出的时刻。

### 14.3 边界与验证

- **键盘**：`P` / `ESC` 在 `PLAYING` 下暂停、在 `PAUSED` 下继续；`PAUSED` 下不接受 `R`
  （键盘玩家按 R 多是手滑，重开在面板上是需要看清才点的按钮）。
- **没有独立暂停层**：面板与结算面板共用 `_dim` 遮罩，但 `show_pause(false)` 只在
  结算面板也不可见时才收遮罩，否则会出现"从暂停直接死亡"时遮罩被提前关掉。
- **`State` 枚举只能往后加**：前四个值会被 `_publish_web_state` 序列化进 JSON 交给
  `shell.html`，插在 `PLAYING` 后面会让前端"加载中 / 已暂停"的判断整体错位。

自检 `dev/ui_pause_check.gd` **32/32**：暂停 30 帧后 `_elapsed` 不动、继续后恢复推进、
选卡/结算时按暂停无效、暂停中重开全部归零、按钮 emit `pressed` 的整条链路、返回后 HUD 隐藏。
与既有的 `dev/pause_check.gd`（外部打断：竖屏 / 切后台）分工不重叠。


## 15. 视野上限、金币与商人、传送确认（2026-11-28 下午）

这一轮七条需求，按依赖顺序落地。最关键的因果链在第 3 条：**「不回血」看起来只是删两行，
实际把经验曲线打崩了一次**，必须一起看。

### 15.1 视野内上限 20 / Boss 战 10

原来的 `_enemy_budget()` 是**全场**预算（随存活时间涨到 79），"视野内会挤多少"没人管。
新增两条闸门，和原来的预算并行：

| 闸门 | 值 | 作用 |
|---|---|---|
| `VISIBLE_ENEMY_CAP` | 20 | 视野（矩形，非圆形）内非 Boss 敌人上限 |
| `BOSS_FIGHT_ENEMY_CAP` | 10 | Boss 在场时同上 |
| `ENEMY_OVERFLOW_ALLOWANCE` | 14 | 全场 = 视野上限 + 14，限制屏外排队长度 |

**超额处理是「推回屏外」，不是删除。** 删除会让怪在玩家眼前蒸发、还不给经验；
推回只是让它晚两秒再走进来，视觉上完全说得通。只推最远的那几只——近身怪突然后跳比消失还假。

三处细节：
- 视野判定用**矩形**（`_view_half()`），圆形近似会把四个角也算进去，上限虚高 27%。
- 刷怪距离下限从固定 480 改成 `_view_radius() * 1.15`：1280×720 / zoom 1.35 下视野半宽只有 474，
  480 的斜向落点会直接落在屏幕里，"刷在视野内"看起来像凭空冒出来。
- Boss 召唤在**召唤前**就算剩余名额（`_visible_cap() - _visible_enemy_count()`），
  不能靠召唤后再推——那会变成"Boss 一挥手，四只怪往外飞"。

### 15.2 传送门：四扇 + 先确认再传送

- 三扇改四扇：单卡 / 双卡 / 破甲弹 +3 / 金币 +90。回血门删掉（传送不再回血）。
- `Portal` 不再自己判"进门就换图"，踩上去只发 `request_enter`；Game 进 `State.CONFIRM`
  弹面板，点「继续前进」才走 `_confirm_portal`。
- 取消后门进 `_leave_gate`：必须走出 `ENTER_RADIUS × 1.7` 才允许再次申请，
  否则玩家站在原地会被同一扇门反复弹面板。
- 台架 `bot.gd` 遇到 `CONFIRM` 直接确认、遇到 `SHOP` 直接关店（不买），
  否则每一局都会卡在门口或柜台前。

### 15.3 「不回血」的连锁反应（本轮最重要的记录）

删掉的两处：升级的 6% 回血、传送门的 HEAL 奖励。`Player` 的脱战自然回复、
Boss 战后 15%、通关补满都保留。

删完之后台架立刻崩了：

| 配置 | 中位 | 单局击杀 | 等级 |
|---|---|---|---|
| 视野 20 + 不回血 + 经验不动（4/12/6） | **158.7s** | 174 | 25 |
| 同上 + 经验 ×2（8/24/12） | **283.3s** | 286 | 32 |

原因是**双重压缩**：视野上限把"能被杀的怪"从屏外几十只压到画面里 20 只，
单局击杀从 1430 掉到 174；击杀少 → 经验少 → 卡少 → DPS 低 → 更清不动。
这不是"变难"，是负循环。经验翻倍把这条链打断之后，中位反超了改动前的 262.2s。

结论写在这里，避免下次有人只删回血、不动经验：**数量是手感，经验是成长，两者必须一起调。**

### 15.4 金币与商人

- 击杀进账：普通 2 / 特殊 3 / 精英 8 / Boss 40。跨图保留，跨局归零。
- 每张图一间**商人密室**（离起点第二远的房间，最远那间留给 Boss）。
  走近 104px 自动开面板，关店后必须走出 168px 才允许再开。
- 三件货，每件每图限购一次：

| 商品 | 价格 | 效果 |
|---|---|---|
| 治疗药剂 | **160** | 回复 40% 最大生命 |
| 破甲弹 ×3 | 60 | Boss 战入场券 |
| 战术手册 | 120 | 立刻一张升级卡 |

回血定价 160 是"相对较高"的具体落点：一张图约 250 击杀 ≈ 540 金，
一瓶药吃掉前 80 秒的全部收入，逼玩家在"续命"和"变强"之间选一个。

### 15.5 地图连通性硬保证

`MazeMap.build()` 末尾加 `_ensure_connected()`：4 邻洪水填充，把每块孤岛接到最近的连通格上，
直到全图可达。走廊本来就是 L 形硬挖、理论上不会断——但"理论上"在这项目里已经出过两次事
（毒圈预算、Boss 预算都栽在它上面）。多跑一次 432 格的 BFS，换"任何 seed 都不会有进不去的房间"。
用 4 邻而不是 8 邻：身体有半径，斜穿墙角实际过不去，8 邻会把死角判成通路。

### 15.7 数值定稿（`e3a3bc4`）

按上面的落点定稿，不再调：`SHOP_HEAL_PRICE 160` / `SHOP_BREACH_PRICE 60` /
`SHOP_CARD_PRICE 120` / `SHOP_HEAL_RATIO 40%`、`Enemy.xp_value` 8/24/12、
`VISIBLE_ENEMY_CAP 20` / `BOSS_FIGHT_ENEMY_CAP 10` / `ENEMY_OVERFLOW_ALLOWANCE 14`。

定稿后在提交节点上重跑同一台架，**逐项复现**（这不是巧合，是这套改动不带随机性）：

| | `kite_skill` | `kite_ranged` | 总体 |
|---|---|---|---|
| 中位 | 259.7s | 356.8s | **283.3s** |
| 最短 / 最长 | 119.0 / 311.9s | 115.4 / 510.0s | 115.4 / 510.0s |

- 战士中位 259.7s、最长只到 311.9s，**没有一局撑过圈归零**——近战在 20 只上限下更容易被围，

- 射手 356.8s、有一局跑满 510s，说明上限对远程几乎没压力。两侧差 97 秒，

## 16. 八项需求：贴顶血条、价格 ×10、属性封顶、穿墙、40 上限、四门难度、破甲弹重做（2026-11-28 晚）

这一轮的八条需求里，有七条是"改一个数"或"加一个闸门"，只有两条会动机制：**攻击不能穿墙**
和**破甲弹重做**。结果就是这一轮把单局时长从 283.3s 打到 161.6s，原因在 §16.9 拆开了。

### 16.1 Boss 血条贴顶

血条原来挂在右侧竖排里，Boss 一开战整块 HUD 会跟着让位。改成**贴屏幕顶部整宽单行**
（名字 + 血条 + 阶段 + 状态字），左右两栏**永久**下移 `TOP_RESERVE = 34.0`
（`corner.position.y` / `right.offset_top`）。只在开战时让位的话，玩家会看到 HUD 跳一下。

`_layout_boss_bar()` 不再按 `_touch_mode` 分叉：桌面和触屏都是 `offset_top = 4`，
宽度交给锚点 `anchor_left = 0.02 / anchor_right = 0.98`——两套数值维护下来
必然出现"手机上好、桌面裁掉一截"。

**让位高度不能写死。** 第一版把 `TOP_RESERVE` 定成 34，渲染截图一看：
左上角的血量条被压掉了上半截。两个原因叠在一起——

1. 血条套的是 `UiKit.panel_style`，它的 `content_margin` 是 **28**（给弹窗写的）。
   一行 22px 高的标签加 56px 边距，面板实际高 78px，比预想的 34 高一倍多。
2. 就算换成窄边距，行高也是字体算出来的，16px 名字 + 13px 状态字混排，写死的数总会差几点。

所以：血条面板改用专用的 `_tight_panel_style()`（上下 5px、左右 14px），
让位高度由 `_sync_top_reserve()` 在 `_build_boss_bar()` 末尾按
`get_combined_minimum_size().y` **实测回写**。`TOP_RESERVE` 只留作量不出来时的兜底。
`stage_check` 补了两条断言（血条底边 ≤ 左/右栏顶边），这类"自检看不出来、截图一眼就有"
的问题必须有一条能自动抓的。

### 16.2 商店价格 ×10，价格随图上涨

| 商品 | 旧 | 新（基础价） |
|---|---|---|
| 治疗药剂 | 160 | **1600** |
| 破甲弹 ×3 | 60 | **600** |
| 战术手册 | 120 | **1200** |

价格公式 `基础价 × (1 + 0.45 × 图数)`，金币进账同步 ×3（普通 2→6、特殊 3→9、精英 8→24、
Boss 40→120）并加 `+30%/图`。**价格涨幅 0.45 故意快于金币涨幅 0.30**：两者相等的话
"价格变高"只是数字变大，购买力一动不动，玩家感觉不到负担。

### 16.3 回血道具：前三图 5%，之后固定 100 点

`_shop_heal_amount()` 一份函数喂两处（货架说明 + 买入结算）。分开写迟早出现
"面板写回 100、实际回 5%"。前三图按最大生命 5%（战士 210 血 = 10 点），
第 4 图起固定 100——后期血量基数大，百分比回血会让"一瓶药回半管"重新变成最优解。

### 16.4 属性 3 倍上限：饱和曲线（`scripts/stat_curve.gd`）

```
mult = 1 + (CAP - 1) × raw / (raw + (CAP - 1))      CAP = 3
```

- 起点斜率 1：第一张卡几乎不打折（实测 +19.8%）。
- 永远小于 CAP：**3 倍是天花板不是目标**，40 张卡合计 2.63 倍。
- 只作用于数值类。计数类（额外弹道、穿透 +1、环绕飞刃 +1）直接改计数，不吃曲线——
  "多一发子弹"没法打折。

实现上有一处必须踩住：`_apply_upgrade()` 拆成"计数类直接改"+"数值类进账本"，
账本只记 `raw`，最终值每次从**出厂值**重算（`_capture_stat_bases()` 在 `_spawn_player()` 末尾）。
拿当前值当新基准的话，上限会在第二次升级时失效。

### 16.5 攻击不能穿墙

三条攻击通道各加一道视线判定，手段不一样，因为它们的几何形状不一样：

| 通道 | 判定 | 理由 |
|---|---|---|
| 子弹 | 逐帧 `maze.has_floor_at(pos)`，不在地板上即灭 | 弹道是点，逐帧判最准 |
| 近战 | 命中前 4 点采样 `_has_line_of_sight()` | 扇形挥砍的端点会甩到墙后，只判端点会"隔墙砍" |
| 回旋镖 | 沿连线 7 点采样 `_has_line_to()` | 只判端点不够：端点落在墙后可走格时照样命中（这是实测抓到的漏） |
| 敌方子弹 | `EnemyShot.maze` 逐帧判，撞墙即灭 | 玩家能躲墙后，怪也得一样 |

### 16.6 视野上限 20 → 40

`VISIBLE_ENEMY_CAP 40`、`ENEMY_OVERFLOW_ALLOWANCE 20`（全场 = 视野 + 20）。
超额仍然是**推回屏外**，不是删除（§15.1 的结论不变）。
这条对时长的影响单独测了：只把它改回 20，中位从 161.6s 回到 182.3s，**约 21 秒**。

### 16.7 四门难度：加法累加，不做连乘

| 门 | 奖励 | 难度增量 |
|---|---|---|
| 单卡 | 1 张卡 | +20% |
| 破甲弹 | +3 发 | +40% |
| 金币 | +90 | +60% |
| 双卡 | 2 张卡 | +100% |

`_floor_power` 累加，`_power_scale() = 1 + _floor_power`。原来的 `1.10^floor` 连乘必须废掉：
一次 +100% 的门走连乘，第五张图就是 32 倍，什么配装都救不回来。
现在四扇门各走一次是 +220%（3.2 倍），四扇双卡门是 +400%（5 倍）——"一直贪双卡"很痛，但痛得可预期。

`Portal.difficulty_text()` 把「+XX%」直接画在门下。不写出来的话，玩家会以为四扇门只是奖励不同。

### 16.8 破甲弹重做：开火即消耗 + 命中必有效果

旧版的问题（上一轮 `breach_check` 的用例里就能看出来）：**窗口外打上去毫无反应**，
而库存又当成"能不能打"的门槛校验——玩家攒了 5 发，在窗口外打掉 3 发，什么都没发生。
体感就是"这东西没用"。

现在：

- 手上有弹 → 下一次攻击自动变穿甲弹（子弹 / 近战整刀 / 回旋镖一次投掷），**开火即扣一发**。
- 命中且在窗口内 → 40 点满额（`BREACH_HIT_DAMAGE`）+ **窗口续 0.6 秒**（`AP_WINDOW_BONUS`）。
- 命中但在窗口外 → 半额 20 点（`AP_OPEN_DAMAGE_RATIO`）+ **直接把 Boss 打进破甲**。
- 普通弹打壳 → 冷色闪光 + 0 伤害，不再走"库存够不够"的判定。

半额那一档是必须的：不然最优解会变成"隔着壳无脑灌弹"。而 0.6 秒的续窗让"手上有弹、
打得够准"能把窗口无限续住——上限由**弹量**控制，不由时间控制。

三章合计仍是 **69 发**（2760 血 ÷ 40），`dev/breach_check.gd` 按新语义整体重写（65 条）。

### 16.9 墙体硬保证与验证

生成入口统一夹紧：`_create_enemy()`、门兜底位置、`_spawn_gem()`、`_spawn_breach()`
都过 `nearest_floor_point()` / `_clamp_into_walkable()`。追击目标点本来就走 `constrain`，
所以"进墙"的路径只有生成和位移两类，两类都堵了。

| 自检 | 结果 | 说明 |
|---|---|---|
| `wall_check`（新） | 12/12 | 12 seed 采样 + 指定墙心造怪 / 追击 / Boss / 门 / 宝石 / 破甲弹 |
| `cross_check`（新） | 10/10 | 四向找「可走-墙-可走」三连格，验四条攻击通道隔墙不打人，各带对照 |
| `stat_check`（新） | 18/18 | 曲线性质 + 40 张卡不越 3 倍 + 计数类不吃曲线 |
| `breach_check` | 65/65 | 按新语义重写 |
| `portal_check` | 53/53 | 四档难度 + 加法累加 |
| `shop_check` | 37/37 | 6/24/9 金币、1600 药价、5% 回血、第 4 图 100 点 |
| `cap_check` | 13/13 | 40 只压制 / Boss 10 只 |
| `maze_check` / `arena_check` / `ui_pause_check` | 63 / 20 / 33 | 未改，回归通过 |

**一处遗留**：`stage_check` 现在有 4 项失败（章节推进 / 章节条归零 / 延迟发卡 / 第 1 章 Boss 出场）。
这 4 项在**本轮改动之前的基线 `08b444f` 上同样失败**（用 `git stash` 验过），
是 §13 把章节循环换成迷宫地图循环之后这个自检没有跟着改——它还在用
`_stage_time = 999` 去催 Boss。不是本轮引入的，但也不能继续挂着：
要么按地图循环重写，要么删掉（Boss 流程现在由 `boss_check` 覆盖）。

### 16.10 台架：单局时长腰斩，原因逐项拆开

同一台架（seed 11–15，kite，10 局），只换配置：

| 配置 | 中位 | 最长 |
|---|---|---|
| §15 定稿 `e3a3bc4` | 283.3s | 510.0s |
| **本轮全量** | **161.6s** | 271.3s |
| 只把四门难度还原成 10% | 199.4s | 401.2s |
| 只把视野上限还原成 20 | 182.3s | 271.6s |
| 只把 CAP 3 改成 100（去封顶） | 152.8s | 312.6s |

读法：

- **门难度 ≈ 38 秒**（161.6 → 199.4）。旧版每图 +10%，现在平均 +55%（台架取最近的门，随机落在四档）。
- **视野 40 ≈ 21 秒**（161.6 → 182.3）。翻倍密度是真代价，但不是主因。
- **属性封顶 ≈ 0**（152.8 vs 161.6，5 个种子内的噪声）。封顶本来就不是"变弱"，
  它是把后期那条陡坡压平；台架活不到后期，所以量不出来。
- **剩下 ~63 秒归"攻击不能穿墙"**（283.3 → 199.4 的 84 秒里，扣掉视野 21、封顶 0）。
  迷宫里隔着墙角的目标太多，bot 又只会朝最近的目标开火，这部分 DPS 是净损失。
  这也解释了为什么射手掉得比战士多。

**商店价格 ×10 在台架上零影响**：`bot.gd` 进店只关不买（§15.6 定的），价格只由 `shop_check` 覆盖。
真实玩家会用脚投票——第 6 张图的药剂 5200，那时候大概率选"不买"。

圈外致死仍是 0/10（§11.6 的目标 15~35% 依旧没达成）。本轮没碰圈，因为需求不涉及；
真要拉回来，先动圈的时间表，别动这几条定稿值。

## 17. 十道门、王座厅、剧情与胜利结算（2026-11-28 深夜）

这一轮的六条需求把游戏从"无限刷"改成了**有终点的十幕**：
最多十道门 → 王座厅连战五位守门人 → 走出西城门 → 胜利结算并记分。
为了让终点不像一个突然弹出的对话框，同一轮里把剧情铺满了全部环节（菜单、每一幕、
五位守门人、死亡、胜利），并且**开场与每次穿门都先播一段**。

### 17.1 需求与拆解

| # | 需求 | 落点 |
|---|---|---|
| 1 | 最多十个传送门，第十个之后只刷 Boss | `PORTAL_LIMIT = 10`，第 10 门后进王座厅 |
| 2 | Boss 死后继续刷，最多 5 个；全灭后出现**一个**门 | `_gauntlet_left/_total` + `Reward.VICTORY` 金门 |
| 3 | 下一屏是胜利结算，积分记到本地 | `State.VICTORY` + `Score.victory_points` + `ScoreBoard.victories` |
| 4 | 王子逃离黑暗城堡的剧情 | `scripts/story.gd`（十幕 + 终章 + 尾声） |
| 5 | 开始与每次穿门先播剧情，可跳过，跳过键在右上角 | `StoryPanel`（CanvasLayer 5）+ `SKIP_MARGIN/SKIP_SIZE` |
| 6 | 剧情相关内容覆盖全部游戏 | 菜单引子 / 章节横幅 / Boss 出场 / 死亡标题与旁白 / 胜利收尾 |

### 17.2 十道门：门数必须单独计数

`_map_index` 同时兼任**幕号**和**章节号**（配色、长度、卡池都读它），
直接拿它当"第几道门"会在换图逻辑里被推两次。所以另起一个 `_portal_count`，
只在 `_confirm_portal()` 里 +1：

```gdscript
var final_hall: bool = _portal_count >= PORTAL_LIMIT
```

第 10 扇门之后不再调 `_rebuild_map()`，改走 `_enter_final_hall()`：
清掉迷宫、换王座厅配色、**补 4 发破甲弹**，然后播终章。

### 17.3 王座厅：五连战

五位守门人是前面见过的老面孔 + 王子自己的影子 + 城堡本身（`Story.GAUNTLET`），
血量按 `GAUNTLET_BASE_SHOTS + GAUNTLET_SHOT_STEP × i` 递增，12/14/16/18/20 发满额（40 点/发）。

**为什么把血砍到原来的一半**：第一版按 16/24/32/40/48 配（合计 160 发），
算下来五场要打 6~8 分钟，一局变成 20 分钟——那不是"史诗"，是"卡住"。
80 发配 1.5 秒的破甲节奏，五场大约 2 分半。

守门人之间的衔接有两个延迟常量，分开是为了各调各的：

- `GAUNTLET_GAP = 2.4`——一位倒下到下一位的空档，够喘气、够捡弹，不够回满血
- `GAUNTLET_BREACH_EVERY = 1.5`——王座厅的破甲窗口比外面密，因为这里没有走位空间

`_gauntlet_left > 0` 会在 `_check_boss()` 和 `_spawn_wave()` 里**同时早退**：
王座厅不刷小怪，也不会有"守门人还没站起来，Boss 门又开了"这种事。

五位全倒 → `_open_final_portal()` 只开**一扇**门（`Reward.VICTORY`，晨光色，拱门形，
门下写「西门外 · 黎明」）。四门那套"选哪扇"在这里是反的——**终点不该给选择题**。

### 17.4 胜利结算与本地存档

胜利与死亡共用 `Score.compute()`，只多一项 `victory_points = 8000`，
并且**胜利奖励取代**原来的"三章通关"奖励（`Stage.is_cleared()` 一并删掉）：
两个都发的话，玩家会算"哪种死法更划算"。

存档 `ScoreBoard` 加两个字段：

- `victories`：逃出次数（主界面与结算里显示"第 N 次逃出城堡"）
- `best_victory{score, elapsed, date}`：**按用时**比，不看分数——
  "最快逃出"是这一版唯一有意义的横向指标，分数会被十道门的奖励选择带偏

旧存档缺这两个字段时按 0 读，`_normalize_victory()` 负责补齐，不清档。

### 17.5 剧情：十幕 + 终章

`scripts/story.gd` 是**唯一**的文本来源：幕名、台词、横幅副标、配色、守门人台词、
死亡标题/旁白、胜利尾声全在这一个文件里（含 `Story.prologue()` 给主菜单的引子）。

一条硬约束写在文件顶上：**每行不超过 24 个汉字**。手机横屏 844×390 CSS 像素，
超过就要换行，换行之后整块文字的排版就散了。所以台词一律"一句一行"。

`StoryPanel` 有三处是踩过坑之后才对的：

1. **必须挂在 `CanvasLayer`（layer=5）下**。Game 是 Node2D，没有矩形，
   `PRESET_FULL_RECT` 在它下面失效，剧情屏会缩成左上角一小团，HUD 从上面穿过去。
2. **不能铺一层不透明 `ColorRect` 做底**。子节点在父节点之后绘制，
   底板会把 `_draw()` 里的烛光与城堡剪影全盖掉（第一版截图只剩纯黑）。底色交给 `_draw`。
3. **跳过键锚点写死在右上**（`anchor_left/right = 1.0`，`offset_left = -22-78`），
   位置不跟正文排版走。一局要弹十次，玩家第二次就会开始找"怎么过快点"。

逐字显示 `CHARS_PER_SEC = 46`、行间 `LINE_HOLD = 2.6`：点一下 **补完当前行**，
再点进下一行；跳过是**一次点击直接到底**，不是跳到下一行（那是十几次点击）。

`story_enabled` 是给自检/台架用的总开关。关掉之后 `_play_story()` **不能直接 return**，
要走一遍 `_on_story_finished(true)`——否则状态永远停在 `STORY`，所有自检卡死
（这一条踩过：`portal_check` 一次挂了 8 项）。

### 17.6 手机端排版：两个只有截图才看得出来的问题

这两条都不是自检抓到的，是**渲染截图**抓到的。

**（1）剧情屏的字在手机上只剩 11 号。** 触屏的逻辑分辨率是 960×540，桌面是 1280×720，
`canvas_items` 拉伸之后 19 号正文落到 844×390 的浏览器里约 11 CSS 像素——剧情屏存在的
意义就是让人读，读不动就白做了。加 `TOUCH_SCALE = 1.28` 一档，跳过键的可点区域同时
从不足 20pt 回到约 26pt。

**（2）胜利面板比手机屏幕还高。** 桌面版胜利面板 587 高，手机能用的高度只有 540，
底部「再来一局 / 换人」两个按钮被屏幕下边缘切掉。修法不是只缩字号，是三处一起：

| 手段 | 省下 |
|---|---|
| `_panel_f()` 全套字号 ×0.82 | ~55 |
| 面板行距 10 → 6（`_clear_panel()` 里统一设） | ~25 |
| 按钮 54 → 46 高 | 8 |

587 → **468**，上下各留 36。`ui_pause_check` 新增了 4 条断言，把视口切成
`KEEP + 960×540` 之后要求两块结算面板**四周至少留 10px**——不是"勉强没超出去"，
贴边在有圆角的手机上会被啃掉一截。验证过：把 `_panel_f()` 改成恒等之后这条会挂
（`panel=8..531 vp=540`），不是一条永远绿的假断言。

| 其余 | arena 20 / cap 13 / wall 12 / stat 18 / cross 10 | 全绿，合计 **427 项** |

字体子集是这一轮最容易漏的地方：台词里出现一个子集外的字，Web 上就是一个方块，
而本地（装了全量 Noto）完全看不出。`story_check` 对**所有**台词与界面固定文案跑
`Font.has_char()`，缺一个字就点名报出来。

### 17.8 台架：单局中位 178.6s，0/10 逃出

同一台架（seed 11–15，kite 两种职业，10 局）：

| 策略 | 中位 | 最短 | 最长 |
|---|---|---|---|
| `kite_skill`（战士） | 193.7s | 152.5s | 251.3s |
| `kite_ranged`（射手） | 163.4s | 123.2s | 211.4s |
| **总体** | **178.6s** | — | 251.3s |

`逃出 0/10`。最远的一局死在第 5 幕、第二只 Boss 手里。这个数**不能**直接读成
"十道门太长"：

- bot 只会朝最近的目标开火、只会绕圈，走位不会用墙角、不吃商人的药、不挑门（随机落在四档）
- 十道门要求玩家在**十次**"贪一点还是稳一点"里都做对；bot 没有这个决策
- 真正要盯的指标是"人能不能在 15~20 分钟里走完一局"，台架回答不了这个问题

但有一条它回答了：**破甲弹的供给**。王座厅补 4 发之后，一路没捡弹的局至少能把
第一位守门人打开；不补的话，那种局是必死的——那不是难度，是死局。

### 17.9 三个待拍板

1. **一局十幕 + 五连守门人的总时长**：台架中位 178.6s（bot 水平），
   人类玩家预计 12~20 分钟。要更长就把幕长调回 70/80/90 以上的节奏，要更短就压门数。
2. **守门人血量档位**：现在 12/14/16/18/20（合计 80 发，约 2 分半）。
   觉得"终局不够重"就整体 +4 发，觉得"打不完"就 −2 发。
3. **王座厅补 4 发破甲弹**这个保底要不要留。留着的那一版，弹尽的人还有一搏；
   去掉之后，"一路捡不捡弹"就成了通关的硬门槛。

## 18. 多结局：选择指向门外，一章三分钟（2026-11-28 傍晚）

两条需求：

1. **创建多个结局，每次选择都会指向不同的结局**；
2. **每一个章节大概三分钟**。

第 1 条的关键不是"多写几个结局"，而是**选择要能被看见**：如果结局只在结算时才揭晓，
玩家会以为那是随机的。所以这一版的落点是三处同时改——记账、显示账本、门与结算同一套数据。

### 18.1 结局挂在"选门"上，不是挂在最后的对话选项上

门是这局唯一**重复十次、每次都有真实代价**的决策（奖励越大，下一幕敌人越强）。
所以十次选门就是十条路。

| 门 | 奖励 | 难度 | 记账名 |
|---|---|---|---|
| 单卡 | 1 张卡 | +20% | `card`（稳） |
| 破甲弹 | +3 发 | +40% | `breach`（战） |
| 金币 | +90 | +60% | `gold`（财） |
| 双卡 | 2 张卡 | +100% | `card2`（贪） |

判定规则写在 `Story.resolve_ending()` 里，四条按顺序：

0. **一次都没选** → 黎明。空账本不能落到"杂色"上，杂色是"四样都试过"；
1. **最大票数 ≤ 3** → 杂色。十次分四类，最大票数至少 3，3/3/2/2 确实没有偏向；
2. **最大票数唯一** → 直接对应；
3. **并列** → 看**最后一次**选的是哪一个（且它必须在并列组里）。
   并列不按固定优先级破：玩家认的是"我最后想要的是这个"，不是"表里它排第一"。

| 结局 | 条件 | 名字 |
|---|---|---|
| 黎明 | 单卡最多 | 什么都没多带 |
| 新的王 | 双卡最多 | 城堡换了一个囚徒 |
| 烧掉的路 | 破甲弹最多 | 你不是推开门，是把门打穿的 |
| 买下的门 | 金币最多 | 没人记得走出来的那个人 |
| 杂色的清晨 | 无主导 | 每样只拿一点 |

### 18.2 账本要在三处可见

只写结算的话，这个机制等于不存在。三处各显示一次，玩家才会把"选择"和"结局"连起来：

1. **选门确认面板**底部一行：`走过的路：稳 2 · 贪 4 · 战 1 · 财 1`
   （带上正在选的这一扇——玩家要判断的是"选完之后我成了什么形状"）
2. **金门下面的字**：`西门外 · 新的王`，不是固定的"黎明"。
   进门之前就知道门外是什么，才是"我的选择指向结局"而不是"抽奖"
3. **结算面板**：`结局 2/5 · 新的王　——　每一道门你都拿了双份` +
   三行收尾 + `已解锁 1/5 个结局`

第 3 条里的"X/5"和"已解锁"是**二周目唯一的钩子**：只写结局名的话，
玩家会读成"这一局有一个结局"，而不是"一共有五个，我见过两个"。

### 18.3 存档：结局图鉴

`ScoreBoard` 的玩家档案加第四个字段 `endings: {"dawn": 2, "throne": 1}`（各见过几次）。
"已解锁 N/5"读的是 key 的数量，不是次数——玩家追的是"见过几种"。
旧存档缺这个字段按空字典读，写回时补齐，不迁移、不清档。
`run_check` 会把 `records.json` 备份再还原，所以自检不会污染真实战绩。

### 18.4 一章三分钟：长度是递减的

这是这一轮最容易被做错的一条。**"每章三分钟"是整章的预算，不是刷怪那一段的预算**：

```
一章 = 刷怪 length + 关底（发数 × 掉率 × 0.6） + 挑门与剧情约 12 秒
```

关底从第一章到第三章是 26s → 35s → 44s。如果三个 length 都写成 140，
第三章就是 196 秒、第六章之后 215 秒——三分钟变成了三分半。

所以三个数是**递减**的：

| 章 | length | 关底 | 合计 |
|---|---|---|---|
| 1 | 142 | ≈26s | **180s** |
| 2 | 134 | ≈35s | **181s** |
| 3 | 124 | ≈44s | **180s** |
| 4~10 | 124 | ≈44s | **180s** |

`ENDLESS_LENGTH_STEP` 从 4 改成 **0**：第四幕起的关底发数与第三章持平，刷怪段就该同样长。
旧版每轮 +4 秒到第 10 幕是 204 秒，一局光小怪就多三分钟，而难度并没有相应上涨。

十幕 ≈ 30 分钟 + 王座厅 ≈ 2 分钟 = **32 分钟一局**。

`breach_check` 把这件事钉成了两条按表算的断言（改 length 或改发数都会自动重算）：
每章 165~200 秒、整局 25~35 分钟。旧的"三章 + Boss 塞进 390 秒毒圈"那条断言
随毒圈一起作废了——它量的是一个已经不在 world 里的东西。

### 18.5 自检

| 脚本 | 结果 | 新增覆盖 |
|---|---|---|
| `story_check` | **57/57** | 五结局数据完整性 + **十种账本判定表** + 路径文案 + 记账入库 |
| `run_check` | **57/57** | 金门副标题 = 这一局的结局、面板写「结局 1/5 · 黎明」、**换一种选择换一种结局且各自入库** |
| `breach_check` | **77/77** | 每章 165~200s、整局 25~35 分（旧毒圈预算断言作废） |

判定表是这一轮最该被钉住的东西：它是五个结局的全部规则，一个数错了，
玩家就会遇到"我一路拿双卡，凭什么给我黎明"——而这种错**不会崩**，只会错。

### 18.6 台架

同一台架（seed 11–15，kite 两种职业，10 局），只换章节长度：

| 配置 | 中位 | 最长 |
|---|---|---|
| §17 定稿（length 70/80/90，一章约 1.5~2 分钟） | 178.6s | 251.3s |
| **本轮（142/134/124，每章 180 秒）** | **201.3s** | **334.5s** |

读法：

- **中位 +23 秒**说明章节变长确实让 bot 活得更久：每章多刷的怪变成经验，等级更高、
  卡更多，撑得住更久。这是"一章三分钟"的副作用，不是 bug。
- **最长从 251s 涨到 334s**，但离 1800s 的整局还差得远，逃出仍是 **0/10**。
  bot 不会挑门（四门里它永远走最近的那扇）、不买药、不用墙角，
  而十道门每道都在逼玩家决定"贪不贪"——这个决策 bot 做不了，所以它测不出通关率。
- 这一轮没有动任何数值平衡，只动了时长。**"一章三分钟"不需要重新配平**：
  难度由 `_floor_power`（每门 +20%~+100%）和 Boss 发数决定，与章节长度无关；
  章节变长只会让玩家多拿几张卡，而那正好抵消后期难度。

## 19. 判定表导出 Excel + 同步 H5 实机验收（2026-11-28 傍晚）

这一轮不是加玩法，是把已经定下来的规则**交出去**：判定表要能被人拿着改、
线上要能被人用手机打开。两件事各暴露了一个真问题。

### 19.1 判定表：三个 sheet，判定列是公式不是结论

`docs/结局判定表-十种账本.xlsx`：

| sheet | 内容 | 关键点 |
|---|---|---|
| 判定表 | 10 行 = `story_check` 里那十种账本 | **B~E 票数改一下，J 列「判定结局」现场重算** |
| 结局一览 | 五个结局的门外名、一句由来、收尾三行 | 「门外」列被判定表 VLOOKUP 引用 |
| 规则说明 | 四条判定顺序 + 常量 + 代码位置 | `MIXED_MAX` / `PORTAL_LIMIT` 改哪个数影响什么 |

判定列没有写死"这一行是黎明"——那样它只是一张**结论截图**，改一个票数就过期了。
写成的是一条可执行的规则链，与 `Story.resolve_ending()` 同序：

```
合计=0 → 黎明
最大票数 ≤ 3 → 杂色
并列数=1 → 取唯一最大
并列 → 最后一次选择落在并列组里就用它，否则退回 稳→贪→战→财
```

公式里最难的是并列破平那一段：先用 `AND(最后一次="贪", 贪票=最大票)` 逐个试，
都不中再退回固定顺序。这正好也是代码里的实现（`last_key` 在并列组内才生效）。

**验算**：重算 54 个公式、0 错误；再读回缓存值逐行比对，五行结局与
`dev/story_check.gd` 的十种账本**逐字一致**（黎明/新的王/烧掉的路/买下的门/
杂色的清晨 ×10）。导出的是"能改的规则"，不是"拍下来的结果"。

## 20. 右上角小地图（2026-11-28 夜）

一条需求：**在右上角加一个小地图**。真正要决定的不是"画在哪"，是**画什么**——
一张把所有东西都标出来的小地图，会把"绕回来撞见一群怪"变成"提前知道"，
那是改玩法，不是加辅助。

### 20.1 位置只有一个候选

屏幕四个角：左下是摇杆、右下是技能键（拇指常驻），左上被血量/幕号/弹数占满。
**右上角是唯一"战斗中不用按"的角**，而且分数已经在那一列——小地图直接挂在
分数与暂停键下面，右对齐，左右不新增一栏。

手机上这一列到小地图底边约 232 逻辑像素（屏高 540），不伸进下半屏，
不会和右下技能键打架。

### 20.2 画什么：雷达内，不是全图

| 元素 | 画法 | 为什么 |
|---|---|---|
| 墙/地板 | 预烘焙纹理 | 只在换图时变，每帧重画 432 格纯属浪费 |
| 玩家 | 白心 + 暗边 + 微光 | 暗边保证落在浅色地板上不糊；微光让眼睛先找到自己 |
| 敌人 | 红点 2×2 | **只画 560 像素内的**，见下 |
| 商人 | 金菱形（实心） | "要不要绕回去"是这一局唯一反复做的取舍 |
| 传送门 | 青色方点 4×4 | 比敌人点大一号：四扇门常挤在同一条走廊，小点会连成虚线 |
| Boss | 橙点 + 外圈 | 值得单独一个形状 |

**560 是"一屏的范围"**：1280×720 @ zoom 1.35 的半对角线约 543。也就是说
小地图只补上"屏幕边缘那一小圈"，不提供隔墙透视。手机上（960×540）
看到的是同一片区域，两个平台不会变成两种游戏。

过滤写在 `Game._sync_minimap()` 里而不是控件里：**"谁算威胁"是玩法判断**
（Boss 战要收紧、屏外排队的怪不该报点），画图控件不该知道这些。

### 20.3 两个只有尺寸才说得清的决定

**1 格 = 5 像素，120×90。** 整数倍不是随手选的：最窄的走廊只有 1 格宽，
5 像素是"还看得见一条线"的下限；4.8 这种非整数倍会把那条线糊成半透明，
地图就退化成噪点。

**120×90 在手机上约 105×79 CSS**（960→844 拉伸），仍然能看清走廊。

### 20.4 顺带修掉的一个真 bug

新自检里有一条"换图后旧的点被清掉"，第一次跑就挂了：`_rebuild_map()` 清了
敌人、宝石、掉落、商人、迷宫，**唯独没清 `_portals`**。正常流程里
`_confirm_portal()` 已经清过了，所以玩法上一直没出事；但"换图"这件事本身
不该依赖调用方先收拾干净——漏一次的后果是上一张图的四扇门留在新图坐标里，
小地图上多出几个走不到的青点，玩家会绕着找根本不存在的门。

已补上点名清理 + `_awaiting_portal = false`。

### 20.5 顺手修掉的一个抖动

`cap_check` 的"视野内已压到 40 以内"偶发 45（三次里挂一次）。查下来不是驱逐
逻辑坏了，是**测试的收敛窗口太短**：`_push_out_of_view` 在找不到视野外的可走格时
会放弃这一次（"宁可短暂超编，也不能把怪瞬移到玩家脸上"），而 headless 的窗口是
**正方形**（1280×1280），视野半径比实际游戏大一截，更容易找不到落点。
0.5 秒只够两轮重试，5 只怪两轮都没被推开就停在 45。

推 1.5 秒（六轮）之后连跑 4 次都是 13/13。为了确认这条断言不是"永远绿"，
把 `_push_out_of_view` 改成直接 return 验证过一次——仍然报 45，说明它量的是
驱逐机制本身。
