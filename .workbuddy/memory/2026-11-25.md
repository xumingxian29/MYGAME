## 12:20 Web 竖屏提示 + 旋转重排（shell.html）

**现状核对（先查再改）**：`project.godot` 里 `window/handheld/orientation=4` **早就有了**
（我上一轮写的）。枚举实测：0=SCREEN_LANDSCAPE / 4=SCREEN_SENSOR_LANDSCAPE（允许左右两个横屏方向）。
用户要求的 `"landscape"` 字符串是非法的——Godot 这个设置是 int 枚举，写字符串会被存成
VARIANT_STRING 且不生效（这条上一轮已经踩过）。**4 才是"横屏"的正确值**，而且比 0 更好用
（0 只锁一个方向）。`display` 段里没有 `display/` 前缀，键是 `window/...`，用
`grep "display/"` 查这个设置会漏，得 `grep "handheld/orientation"`。

**shell.html 三处结构性改动**
1. **竖屏层 `#rotate`**：全屏不透明（`inset:0` + `var(--bg)`），手机图标（44×76 圆角框 +
   底部横条）+ 大字「请把手机横过来」+ 副标题 + 一行进度文字。显示条件用
   `@media (orientation: portrait) and (pointer: coarse)`，另加
   `(orientation: portrait) and (max-width: 820px)` 覆盖报 fine pointer 的国产 WebView；
   桌面把窗口拖成竖的（宽 > 820）不加这层，否则会对着能玩的画面弹"请把手机横过来"。
   **纯 CSS 判定**：引擎 39MB wasm 还在下载时提示就必须在，不能等 JS。
2. **进度坞 `#loadbar`**：`position:fixed; bottom:12%; left:50%; transform:translateX(-50%)`，
   z-index 30（压过竖屏层的 20）。竖屏时玩家看到「提示 + 底下一条还在走的进度」，
   这正是反馈里"竖屏以为加载不出来"的正解。
   **关键坑**：`#loadbar` 一开始是 `#status` 的子元素，而 `#status` 有 `z-index:10` →
   形成层叠上下文，子元素再高的 z-index 也压不过 z-index 20 的竖屏层（进度条被整块盖住）。
   必须把它挪成 `#status` 的**兄弟节点**。
3. **旋转重排**：`resize` / `orientationchange` / `visualViewport.resize` 三处都听；
   `applyViewport()` 只做一件事——给 window 重新派发一次 `resize`（`selfDispatch` 标志挡住
   递归），因为 Godot 的 canvas 尺寸与缩放都挂在自己的 resize 链路上
   （`GodotDisplayScreen.updateSize()` 每帧读 `window.innerWidth`）。
   **不要自己去改 canvas 宽高**：引擎按 `devicePixelRatio` 写行内样式，插手会糊或留白。
   `orientationchange` 先立刻补一次，320ms 后再补一次（iOS 旋转动画期间 innerWidth 还是旧值，
   这是"转过来黑一下"的主因），再加 700ms 兜底。

**Godot 侧**：`game.gd` 的 `_ready()` 末尾接 `get_viewport().size_changed` →
`_on_viewport_size_changed()`，`_touch_mode` 时重设 `content_scale_size = 960x540`。
理由不是 web（web 上 stretch 自己会重算），而是 **Android 旋转会重建窗口**，
运行时设过的 `content_scale_size` 会被重置回 project.godot 的 1280x720，
而 HUD/触屏控件按 960x540 布的局 → 字变大、按钮跑出屏幕。

**验收（新仪器 `dev/web_rotate_check.mjs`）**：原生 CDP 驱动无头 Edge，
`Emulation.setDeviceMetricsOverride` 切 390×844 ↔ 844×390，**32 项断言全过**：
- 加载中竖屏：提示层 flex、铺满 390×844、文案正确、进度坞 `[55,713,281,30]` 在屏内、
  底部留白 101px = 12%×844
- 加载中来回转 2 次：提示层跟着方向显隐，进度坞始终在屏内，进度值 181500→1785000 没被打回 0
- 引擎起来后（canvas>1000）：来回转 3 次，每次 `canvas.width=1688=844×2(dpr)`、
  rect 填满视口、无黑边
- 加载完成进菜单；**加载完再竖屏**提示层照常出现且文案变「加载完成 · 横屏即可开始」

**踩坑（测试侧）**：
1. 本地回环几百毫秒就拉完 39MB wasm，`#loadbar` 已被 `finishLoading()` 移除，断言全打到 null。
   必须 `Network.emulateNetworkConditions` 限到 600KB/s 才有"加载中"可验。
2. **引擎 init 之前 canvas 是默认 300×150**（`GodotDisplayScreen.updateSize` 还没跑），
   这时候断言 canvas 尺寸必然是 FAIL。验收要分两段：加载中只验版式，引擎起来后再验 canvas。

## 12:35 竖屏暂停（shell → 引擎双向桥）

**需求**：竖屏时冻结游戏，横屏回来继续。上一轮留的产品决定，这次做了。

**桥怎么搭（Godot 4 Web）**
- 引擎 → 注册回调：`JavaScriptBridge.create_callback(_on_web_portrait)`，
  挂到 `JavaScriptBridge.get_interface("window").__nsPortrait`。
  **返回值必须用成员变量存住**（`_web_portrait_cb`），否则被 GC 回收、回调静默失效——
  这是 Godot 文档明说但很容易漏的一条。
- 回调入参永远是 **Array**（不是单个值），`int(args[0])` 取。
- shell → 引擎之前可能已经推过方向（玩家竖着打开页面），那时回调还不存在、消息丢了。
  所以引擎 `_ready` 里反向 `JavaScriptBridge.eval("window.__nsPushPortrait()")` 主动要一次。
- 引擎 → shell：`window.__nsState = JSON.stringify({paused, portrait, state, elapsed})`。
  shell 用 `Object.defineProperty` 把 `__nsState` 定义成 accessor，
  setter 里刷新竖屏文案——引擎一改状态 UI 立刻跟着变，不用轮询。

**暂停语义（关键，不是 `paused = true` 就完事）**
- 单独一个 `_portrait_paused` 标志，**不复用 `_state`**：竖屏是外力打断，不是状态转移，
  玩家横屏回来必须回到他离开的那个状态。
- `_unpause_if_ready()`：`paused = _portrait_paused or _state != PLAYING`。
  选卡（LEVEL_UP）和结算（GAME_OVER）横屏回来必须**仍然暂停**——
  否则玩家一转身就"带着没选的卡挨打"或"死亡结算被跳过直接回到游戏"。
- 开局/选卡结束那两处原本硬写 `get_tree().paused = false`，改成走 `_unpause_if_ready()`：
  竖屏状态下开局（bot 与自检会直接调）必须保持冻结。
- `_process` 里每帧调一次 `_publish_web_state()`，内部按 (state, paused) 去重；
  `_state` 的写点散在 4 处，与其到处埋调用不如让主循环兜住。没变化时只是一次 int 比较。

**shell 判定用 matchMedia，不是 `innerHeight > innerWidth`**
`(orientation: portrait) and (pointer: coarse), (orientation: portrait) and (max-width: 820px)`
——和 CSS 里 `#rotate` 的显示条件**逐字一致**，否则会出现"没显示提示但游戏被暂停"的哑巴状态。
桌面把窗口拖成竖的（宽 > 820、fine pointer）画面照样能玩，不该弹提示也不该暂停。
媒体查询自带 `change` 事件，比 `orientationchange` 更早更准（部分安卓 WebView 要等旋转动画结束）。

**文案分两档**：加载中「请把手机横过来」，加载后（读 `__nsState.state`）——
PLAYING/LEVEL_UP 时「已暂停 / 竖屏时游戏会自动暂停，横过来接着打」，
MENU/GAME_OVER 时「请横屏继续」。

**验证**
- `dev/pause_check.gd`（新）**22 项全过**：竖屏冻结但 `_state` 不变、重复推幂等、
  横屏恢复、选卡/结算/菜单三种非 PLAYING 状态下横屏不偷跑、竖屏开局仍冻结、
  空参数不崩、非 web 平台桥不建立且 `_publish_web_state` 是空操作。
- `dev/web_pause_check.mjs`（新，原生 CDP）**29 项全过**，端到端：
  点「开始游戏」进 PLAYING → 竖屏 `paused=true` 且 `state` 仍是 1 → 横屏 `paused=false`，
  来回 3 轮；**局内时间竖屏 5.2→5.2 冻死、横屏 5.2→7.3 恢复**；
  桌面 1280×900 竖窗口不暂停不弹提示。
- `dev/stage_check.gd` 55 项、`dev/boss_check.gd` 38 项、`dev/web_rotate_check.mjs` 32 项
  全部回归通过。

**踩坑（测试侧）**
1. `waitState` 超时返回旧值会让"有没有点进游戏"这类断言**永远通过**——

## 12:45 切后台也暂停（把"竖屏暂停"重构成原因集合）

**需求**：切后台同样冻结，"别带没选的卡挨打"。

**重构**：`_portrait_paused: bool` → `_external_pauses: Dictionary`（"portrait"/"hidden" → true）。
不是加第二个 bool 然后 `a or b` —— 手机上的真实场景是"竖着切到微信、回来还竖着"，
两个原因同时成立时，先解除的那个不能把游戏放跑。集合天然处理这件事。

- 桥接口从 `window.__nsPortrait(1/0)` 改成 `window.__nsPause(reason, on)`，
  `__nsPushPortrait` → `__nsResync`（重推全部原因）。
- `_unpause_if_ready()` 改名 **`_sync_pause()`**：`paused = not _external_pauses.is_empty() or _state != PLAYING`。
  所有解除暂停的路径都走它，**不许直接写 `paused = false`**——这正是"别带没选的卡挨打"的落点。
- `__nsState` 多一个 `reasons` 数组，方便前端与测试看清"现在因为什么停着"。

**shell 侧事件选择**
- 主用 `visibilitychange`（`document.hidden`），**不用 blur**：桌面点一下地址栏也会 blur，
  但页面还看得见，那时暂停只会让人莫名其妙。
- 补 `pagehide` / `pageshow`：移动端切后台有时只有这两个（甚至走 bfcache）。
- `reportPause(reason, on)` 是唯一出口，竖屏与后台共用，`dataset.paused` 同步给 CSS。

**验证**
- `dev/pause_check.gd` 从 22 项扩到 **32 项全过**：新增切后台、双原因叠加
  （解除竖屏仍暂停 → 解除后台才恢复）、**选卡时切后台回来不偷跑**（`state` 仍是 LEVEL_UP
  且 `paused` 仍为 true）、结算/菜单同理、后台中开局仍冻结、缺参数/空原因不崩。
- `dev/web_pause_check.mjs` 从 29 项扩到 **36 项全过**：
  切后台 `reasons=["hidden"]`、竖屏+后台 `reasons=["portrait","hidden"]` 时转横屏仍 paused、
  后台期间 `elapsed 8.9→8.9` 冻死、回前台 `8.9→10.8` 恢复。
- `stage_check` 55 / `boss_check` 38 / `web_rotate_check` 32 全回归通过。

**踩坑（测试侧）**
- 模拟切后台**不能用** `Page.setWebLifecycleState('frozen')`：它会把页面脚本执行一起冻住，
  冻住之后 CDP 的 `evaluate` 也跑不了，等于没法验证冻住之后的状态。
  改用"`Object.defineProperty(document,'hidden')` 劫持 + 派发真实 visibilitychange"——
  只改这一个属性，shell 的监听器与传值路径都是真走了一遍。
- 自己写的断言也会错：`_reasons().is_empty()` 里 `_reasons()` 返回的是 `"reasons=[]"` 字符串，
  永远非空。判断集合空要用 `_external_pauses.is_empty()`。

## 18:00–18:40 修「后期屏幕十分震荡」：两个独立病因

### 病因一（主因）：震动频率超出 60fps 能表达的范围
`_tick_shake` 里 `_shake_t += delta * 46`，四项倍频 1.7/2.9/2.3/3.7
→ **12.4 / 16.8 / 21.2 / 27.1 Hz**。换算成每帧相位推进 = **75°~127°**。
一帧转过 90°，下一帧的方向和上一帧没有关系，采样出来就是白噪声。
逐帧 offset 实测（trauma 钉在 0.7）：
```
-0.2,2.8 → 8.5,4.2 → -0.4,-9.4 → -8.4,4.8 → 0.6,2.3 → 2.7,-1.1 ...
```
相邻帧跳 17 个世界单位（23 屏幕像素），**比振幅本身还远**。

### 病因二：击杀持续注入 trauma，永不归零
`_on_enemy_killed` 里 `add_trauma(0.25 if tier>0 else 0.04)`。
单个 0.04 的幅度只有 26×0.04² = 0.04 单位 ≈ **0.06 像素**，本来就看不见；
它的作用全部来自累加：后期实测 **13~25 击杀/秒** → 0.5~1.0/s 持续注入，
衰减只有 1.7/s → trauma 稳态 ≈ 0.4，屏幕以 6 像素幅度**永远在抖**。
这是"后期才出现"的直接原因：早期 1 击杀/秒时稳态只有 0.02。

### 改法
`scripts/player.gd`
- `SHAKE_HZ = 5.4`（每帧 32°，5.6 帧走完半周期），细节分量 1.6 倍频 + 0.3 权重
- `SHAKE_DEADZONE = 0.9`：amp 不到 1 像素直接归零，不留"渐弱到 0"的尾巴
  （渐弱过程本身就是一段永远停不下来的微抖）
- `TRAUMA_DECAY 1.7 → 1.9`
- `_tick_shake` 从 `_physics_process` **挪到 `_process`**：物理固定 60/s、渲染可能是
  30 或 120，不对齐时同一个 offset 会被连续两帧共用 → 阶梯位移，比抖动更难看
- 新增 `_notification(NOTIFICATION_PAUSED)` 回正：暂停后 `_process` 停推进，
  偏移会冻在最后一帧，选卡面板背后的世界就是歪的（最多 34px）
- 受击 0.55 → 0.50（频率降下来后同样的峰值感知更重）

`scripts/game.gd` / `scripts/skills.gd`
- **普通击杀 trauma 0.04 → 0**，精英 0.25 → 0.15
- 技能 0.50/0.45/0.35 → 0.40/0.35/0.27（技能每 3 秒一次、衰减 0.21s，本来就不累加，
  只有按"感知变重"下调一点，不用砍狠）
- Boss 阶段 0.5→0.4、瞬移 0.3→0.25、死亡 0.7→0.6、通关 0.9→0.8

### 测量方法（值得复用）
`dev/shake_shot.gd`：清空敌人 + 关刷怪 + 锁血 + 把 trauma 钉住，连拍 12 帧。
场上没有敌人时**唯一画面变化就来自相机震动**，于是"相邻帧平均像素差"直接等于震动强度。
校准：trauma=0 时差值 **0.000**，trauma=0.7 时 **0.765** —— 基线是真正的零。
但像素差只能说明"在动"，**说明不了"动得连不连贯"**，所以关键指标是：
**帧间跳变 / 峰值位移**。平滑正弦 ≈ 0.36（均值），白噪声接近 1.4。
实测 **1.07 → 0.46**。

## 高刷新率重影 = 物理插值（18:45 收尾，就是上面那条"并行会话"）

**病因不是猜的，是量的**：`dev/interp_probe.gd` 在 `--fixed-fps 240` 下读相机画布变换的逐帧增量。
改前 **75.1% 的渲染帧画面完全没动**（同一个物理位置被画了 2~4 次）、变异系数 1.74 —— 这就是"重影/顿挫"。
逻辑全在 `_physics_process`（60Hz）、渲染在屏幕刷新率上，中间没有补帧，仅此而已。

**修复只需要一行**：`project.godot` → `[physics] common/physics_interpolation=true`。
改后静止帧 **0.0%**、CV **0.00**、240Hz 每帧位移 1.271 像素（= 226×1.35÷240 的理论值）；120Hz 同样全绿。

- **相机不用管**：引擎会自动把 Camera2D 切到物理进程（启动时打一行
  `WARNING: Camera2D overridden to physics process mode due to use of physics interpolation`，
  这是**正常提示不是报错**，别去查）。画布变换实测滞后 0.88 tick，说明它已经被插值。
  不要给相机加 top_level 手动跟随——那会变成滞后两倍。
- **坑 1：生成/瞬移必须 `reset_physics_interpolation()`**。新节点的"上一个变换"是默认值（世界原点），
  不重置就会从原点滑到出生点。像素实测（`dev/spawn_probe.gd` 品红圆点质心）：
  不重置时 240Hz 下生成滑 **197 像素**、瞬移滑 **237 像素**；重置后 **0.00**。
  7 处生成点（刷怪 / Boss / 弹幕 / 追踪弹 / 吐息弹 / 宝石）+ 蚀影瞬移。
- **坑 2：数组自绘的武器引擎管不到**（插值只作用于 CanvasItem 变换）。子弹/回旋镖/飞刃/刀光
  必须在 `_process` 里 `queue_redraw()`，并在 `_draw` 里按 `Engine.get_physics_interpolation_fraction()`
  自己插。子弹用局部坐标 `lpos/plpos` 插：`lerp(a,f)+lerp(b,f)==lerp(a+b,f)`，锚点抖动正好抵消。
- **坑 3：飞刃 `_angle` 是判定量，不能顺手去掉 fmod**。试过，同一颗种子的整局时长从 307s 飘到 161s。
  绘制量另开 `_draw_angle`（不取模）给插值用，判定继续用取模的 `_angle`。
- **2D 没有 `get_global_transform_interpolated()`**（只有 3D 有），GDScript 读不到插值后的坐标。
  验证只有两条路：读 `get_canvas_transform()`，或截图像素质心（`dev/spawn_probe.gd` 就是这么做的）。

**A/B 证明"插值只动画面"**：同一迭代数下，开关插值各跑一次，`Engine.get_physics_frames()` 都是 194、
玩家终点坐标都是 `(726.9661, 0.0)` —— 物理逐位一致。

**⚠️ bot 局不是复现器**：同一份构建连跑两次，`kite_ranged` 308.5 / 309.0、`idle_skill` 163.7 / 163.2

每个进程都不同。**别拿单局数字做 A/B**，只能看 20 局中位数。
